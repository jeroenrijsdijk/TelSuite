GPS Snap
Methodology

telonline.org — adjacency-aware road snapping
This document describes how GPS fixes are matched to OSM road geometry in telonline.org. The snap is what links every observation to a specific way_id and seg_idx; the quality of that match determines whether the downstream reports (telrapport.html) attribute counts to the correct street.
Scope At the time of writing, the adjacency-aware algorithm described below lives only in pocket_count.html. The other survey apps (parkeertelling.html, fietsparkeren.html, capaciteitstelling.html) still use a stateless nearest-edge snap and will be migrated in a later round. Until then, the same edge-case bugs described below can still occur in those tools.
Note on bearing — parking surveys parkeertelling.html, fietsparkeren.html and capaciteitstelling.html attach a zijde (side: left/right of the way) to each observation, derived from the GPS movement vector. This bearing logic is independent from the snap algorithm: snap answers "which way am I on", bearing answers "which side of it am I observing". They are coupled only at output time, when both values are written to _capaciteit.csv or _straten.csv.

When migrating the adjacency-aware snap to these apps, the bearing code is not touched. A risk to keep in mind: if the snap holds anchor on way A while the counter is physically on parallel way B, the recorded zijde will be valid for A but incorrect for B — a compound error rather than a single one. In practice parking surveys run along well-defined linear streets where snap pathologies (jitter at standstill, level transitions in covered passages) are rare, so this risk is mostly theoretical. A separate document will be written if field tests reveal bearing/snap interaction issues after migration.

1. The problem

The previous snap algorithm was stateless: for every GPS fix, the closest OSM edge within SNAP_MAX_M = 50 m was selected. This works well in open suburban streets but breaks down in dense urban fabric.

The canonical failure case — observed in ZIP 20260520_145913_txb_pkt — involves two parallel pedestrian ways in Spijkenisse Centrum:

  • 136079346: one of two near-parallel pedestrian passages
  • 130419432: the other, roughly 8 m away

Both ways are well within the 50 m radius. Because GPS accuracy in narrow urban canyons is typically 5–15 m, individual fixes wobble between the two candidates, and the stateless snap — having no concept of topology — flips attribution between them. This is the general failure mode the adjacency-aware snap exists to fix: where parallel ways are genuinely disconnected (no shared node, reachable only via a cross-street), topology can rule out the unreachable one.

A caveat specific to this ZIP: re-analysis under v2.8 (see §8) showed that taps 28, 29, 44, 45 actually sit on a junction where 130419432, 136079346 and 130418057 converge within sub-metre — far below GPS accuracy. That is a distinct, irreducible case rather than the parallel-disconnected one: no distance- or topology-based rule can separate candidates that occupy the same point in space. The adjacency snap still addresses the broad parallel-ways problem; it simply cannot resolve a true shared-node junction.

2. The core idea

Movement on a road network is constrained by topology, not by Euclidean distance. A counter on Centrumpassage cannot suddenly be on Nieuwstraat-west on the next fix without traversing a connecting way. The fix is to make the snap state-aware: each GPS fix snaps to a way that is reachable from the previously snapped way through the adjacency graph.

GPS is no longer consulted as ground truth for "which way am I on" — only "which fix is the closest evidence". The decision about which way is filtered by the network's topology. Taps inherit the currently snapped way; they do not run their own independent snap pass.

3. The adjacency graph

Two OSM ways are adjacent when they share at least one node (by node ID, not by coordinate proximity). This catches T-junctions, roundabouts, and multi-way intersections correctly: an intermediate node halfway along a way still connects whatever ways meet there.

Acquiring the data

The Overpass query in pocket_count.html uses out body geom; rather than out tags geom;. The body verb adds the nodes array (a list of node IDs in order) to every way element, which is exactly what we need for the adjacency check. Geometry is still included.

Construction

The graph is built incrementally as the Overpass fetches expand the working area:

Adjacency registration (pseudocode)
for each way in overpass_response:
    for each node_id in way.nodes:
        if node_to_ways[node_id] already contains way.id:
            continue  # already registered on this node
        for each other_way_id in node_to_ways[node_id]:
            adjacency[way.id].add(other_way_id)
            adjacency[other_way_id].add(way.id)
        node_to_ways[node_id].add(way.id)

Both node_to_ways and adjacency grow cumulatively over the lifetime of a session. New fetches add new edges; existing edges are idempotent. This matters because the anchor must remain valid across refetches when the counter walks into newly fetched terrain.

Candidate accumulation across refetches (v2.8)

The geometry must accumulate the same way the graph does. Before v2.8 the snap-candidate set was rebuilt from each fresh Overpass response, so a way that fell just outside the new fetch circle lost its candidacy at every refetch — the counter could walk back onto a way that had vanished from the pool. v2.8 makes the pool cumulative:

  • snapElements accumulates every way ever fetched in the session; it is never rebuilt.
  • snapElementsNear(lat, lon) derives the per-fix candidate list from that cumulative pool, keeping any way with at least one node within SNAP_SEGS_RADIUS (400 m). The current anchor is always retained regardless of node distance, so the way you are standing on can never drop out — even a long way with widely-spaced nodes.
  • The fetch order is now accumulate first, build second: new elements are merged into snapElements and snapAdjacency, then snapBuildSegs reprojects everything against the current origin in one pass. A single origin avoids mixing coordinate frames from different fetches.

Each fetch logs n_el|n_kept|n_segs to _snap_trace.csv: total cumulative ways, ways kept within SNAP_SEGS_RADIUS, and segments handed to the matcher.

4. The snap algorithm

Each GPS fix passes through a five-step decision ladder. The output is either a snap object (with wayId, segIdx, snapped coordinates) or null — the latter meaning "this fix did not produce a confident match, keep the current anchor".

snapNearestWay() — decision ladder
def snap(lat, lon):
    candidates = nearest_edge_per_way(lat, lon)  # {wayId → distance, segment}
    candidates = {w: c for w, c in candidates if c.distance <= SNAP_MAX_M}

    # Step 1 — bootstrap: no anchor yet (start of session)
    if anchor_way_id is None:
        chosen = closest_in(candidates)
        set_anchor(chosen)
        return chosen

    # Step 2 — depth-1: anchor + directly connected ways
    allowed = {anchor_way_id} ∪ adjacency[anchor_way_id]
    chosen = closest_in(candidates ∩ allowed)
    if chosen:
        update_anchor(chosen)
        return chosen

    # Step 3 — depth-2: also neighbours-of-neighbours
    # (catches short skipped ways at speed, e.g. driving)
    allowed = expand_adjacency(anchor_way_id, depth=2)
    chosen = closest_in(candidates ∩ allowed)
    if chosen:
        update_anchor(chosen)
        return chosen

    # Step 4 — reset check: is the anchor itself too far away?
    if distance_to_way(lat, lon, anchor_way_id) > SNAP_RESET_M:
        clear_anchor()
        chosen = closest_in(candidates)
        set_anchor(chosen)
        return chosen

    # Step 5 — glitch hold: probable GPS jitter, keep anchor
    return None

Why this order matters

Depth-1 is tried before depth-2 because depth-2 sets are much larger in dense networks. In a city center, depth-2 from any anchor typically covers half the neighborhood; checking depth-1 first preserves the filter's discriminating power for the common case (walking pace, 1 Hz GPS, fixes within the same way).

The reset check uses the anchor's own distance, not the candidate distance, because we want to distinguish "the counter has moved away" (anchor far) from "the GPS is glitching" (anchor still near but no connected candidate visible right now). Without this distinction, every tunnel exit would corrupt the anchor.

5. Tunable parameters

Four numerical knobs govern the live snap's behavior. All are defined as top-level constants in the snap module. (The offline reassignment in §7 has its own internal constants.)

ConstantDefaultWhat it does
SNAP_MAX_M 50 m Maximum perpendicular distance from a GPS fix to an OSM edge for that edge to be considered as a candidate. Anything beyond is silently discarded. Increasing this helps in areas with poor OSM coverage but admits more noise; decreasing it makes the snap stricter but increases the rate of null outputs (Step 5).
SNAP_RESET_M 50 m Threshold for declaring that the counter has physically moved away from the anchor. When the anchor itself lies further than this from the current GPS position and no connected candidate is found, the anchor is cleared and the next fix is treated as bootstrap. Set equal to SNAP_MAX_M: an anchor that is already out of snap range cannot be a useful constraint, so there is no reason to hold it longer.
SNAP_SEGS_RADIUS 400 m Radius around the current fix within which a cumulatively-fetched way stays in the candidate pool (see §3). Derived as round(SNAP_ROAD_FETCH_RADIUS × 1.6) from the 250 m fetch radius plus the maximum drift before a refetch. Larger values keep more far-off ways as candidates (more robust when doubling back, slightly more work per fix); the anchor is always kept regardless of this radius.
adjacency depth 1, then 2 The algorithm tries depth-1 first, falls back to depth-2 if depth-1 yields no candidate. Not a tunable scalar but a fixed two-stage fallback. In principle a depth-3 stage could be added for very high speeds, but at >120 km/h on a 1 Hz GPS the snap is already losing meaning.

Speed adaptivity is automatic

The two-stage depth ladder gives the algorithm an emergent property: at walking pace, fixes are dense and depth-1 nearly always succeeds, keeping the filter strict. At driving speed, individual ways may be skipped between fixes; depth-1 then comes up empty, depth-2 picks up the slack. No explicit speed estimate is needed.

6. Tap anchor inheritance

User taps (counting actions) do not run their own independent snap. When a tap fires, the handler asks the snap module for a fresh snap at the current GPS position. Two outcomes:

  1. Fresh snap succeeded (Steps 1–4 returned a result) — the tap stores that result's wayId, segIdx, and osmName.
  2. Fresh snap returned null (Step 5: glitch hold) — the tap inherits the current anchor's wayId and segIdx, plus the cached osmName from snapElements[anchor].

Inheritance is preferred over emitting an empty wayId because we know more than the absence of a fresh snap suggests: the anchor was valid one fix ago, the counter cannot have teleported, so the most defensible attribution is the anchor itself. In practice this turns short GPS dropouts (passing under a bridge, stepping into a doorway) from data gaps into correctly-attributed taps.

Inheritance does not apply during bootstrap: if anchor_way_id is still null when a tap fires (very first tap of a session, before any GPS fix has resolved), the tap is held in snapPendingQueue as before.

7. Offline trajectory reassignment (v2.8)

The live snap (§4) and live tap inheritance (§6) are necessarily causal: at each fix they know only the past. The anchor tempers jitter but can stick to a distant anchor way, and it cannot use evidence that only arrives later. Once a session ends the whole trajectory is known, so v2.8 runs a single global correction — reassignTrajectory() — just before the ZIP is built. It rewrites the snapped way and segment of every fix and every tap from the complete path, topology first.

Hoe het werkt — stap voor stap

Het algoritme kijkt naar alle GPS-punten in je sessie als één compleet plaatje en zoekt het meest waarschijnlijke pad door het wegennet — het pad dat zowel aansluit bij wat je GPS zei, als ook topologisch realistisch is (dus langs echte wegen en hun samenvoeging).

  1. Stap 1: Verzamelen. Voor elk GPS-punt zoeken we alle wegen uit het wegennet die in de buurt liggen — binnen 40 meter. Deze kandidaat-wegen zijn de plekken waar je *zou* kunnen zijn. Voor elk kandidaat meten we twee dingen: (a) hoe dicht het GPS-punt daadwerkelijk bij die weg ligt, en (b) hoe goed staat de nauwkeurigheid van het toestel op dat moment.
  2. Stap 2: Afweging per kandidaat. Kandidaat-wegen die *dicht* bij het GPS-punt liggen krijgen een lagere "strafkost". Kandidaten die *ver* weg liggen krijgen een hogere straf. Maar: als je toestel op dat moment heel slecht werkt (grote onzekerheidscirkel), maken die verschillen niet zoveel uit — dan geeft het algoritme alle kandidaten meer gelijke kans. Dit is fair: een slechte GPS-meting zegt niet veel, dus vertrouwen we er niet blind op.
  3. Stap 3: Topologie — de wegenkaart als leidraad. Nu komt de slimheid: het wegennet zelf zegt iets. Wegen zijn verbonden op kruisingen (een gedeelde knoop in de kaart). Als je vorige GPS-punt je op weg A plaatste, dan is het waarschijnlijker dat je volgende punt ook op weg A ligt, of op een weg die eraan vast zit, dan op een weg die kilometer verderop ligt. Dus: voorblijven op dezelfde weg kost geen extra straf. Naar een direct verbonden weg hopppen kost een kleine straf. Naar een weg die twee hoppen weg is kost meer. Alles verder is niet toegestaan — je loopt niet zomaar door de lucht naar een weg.
  4. Stap 4: Staplengtes helpen mee (v2.8 toevoeging). Naast de afstanden meten we ook de *lengte* van de stap die je GPS-apparaat zegt dat je zette. Als je echte stap op de weg (gemeten langs de geproject punten) overeenkomt met je werkelijke GPS-stap, is dat een extra aanwijzing dat we op de juiste weg zitten. Dit helpt kiezen tussen wegen die even dichtbij liggen.
  5. Stap 5: Koersrichting — waar loop je heen (v2.9 toevoeging). We kijken ook in welke richting je GPS zegt dat je loopt (bereken uit twee opeenvolgende punten), en in welke richting de kandidaat-weg wijst. Als je noordwaarts loopt en er liggen twee wegen even dicht bij je huidige plek, maar één loopt north-south en de ander oost-west, dan is het waarschijnlijker dat je op de north-south weg bent. Dit helpt vooral wanneer je GPS slecht is (grote onzekerheidscirkel), want dan zegt de richting meer dan de afstand.
  6. Stap 6: Het beste pad vinden. Met al deze "strafkosten" (afstand, topologie, staplengte, richting) zoekt het algoritme het pad van het begin tot het eind van je session dat de laagste totale straf heeft. Dit pad is het meest waarschijnlijke: het past het beste bij je GPS, de topologie en je beweging.
  7. Stap 7: Segmenten bepalen. Wegen zijn lang, dus worden ze voor analysedoeleinden opgedeeld in stukken van ongeveer 40 meter (segmenten). We bepalen voor elk GPS-punt in welk segment van zijn gekozen weg het ligt, zodat we later precies kunnen zien waar je telde.
  8. Stap 8: Tikken (telling-momenten) meedenken. Je had twee gegevensbronnen: GPS-punten en tikken (jij tikt manueel aan wat je ziet). Elk tik-moment wordt gekoppeld aan het GPS-punt dat er het dichtst bij ligt in de tijd. Op die manier zit je tik en je positie op hetzelfde wegsegment — ze horen logisch bij elkaar.
  9. Stap 9: Als het netwerk verbroken is. Soms springt je GPS naar een plek waar het wegennet niet aansluit op je vorige positie (je loopt bijvoorbeeld door een gat in de kaart, of een zwak GPS-moment). Dan begint het algoritme daar gewoon opnieuw met het beste pad vandaar. Elk "stuk" van de route (van begin tot gat, van gat tot einde) krijgt zijn eigen optimale pad. Dit voorkomt dat één gat de hele route verpest.

Waarom offline beter is dan real-time. Tijdens je wandeling werkt de live snap (§4) stap voor stap: elk nieuw GPS-punt probeert onmiddellijk vast te stellen welke weg je op bent. De algoritme kent maar het verleden — wat er straks komt weet hij nog niet. Dat betekent dat hij soms "vast raakt" op een oude weg en niet eenvoudig kan overstappen, ook al wordt later duidelijk dat je eigenlijk naar een andere weg had moeten gaan. Pas nadat je sessie helemaal klaar is, heeft het algoritme alle informatie — je hele pad, je hele richting, alles. Dan kan het achteraf zeggen: "Ik zie nu dat je hier was, en je beweging hierna maakte duidelijk dat je eigenlijk hier had moeten zijn." Dit offline-pad is meestal veel beter dan wat live kon worden geraden.

Verified on field session 20260529_162037_xax_pkt: 33 taps the live snap had left on service ways moved onto pedestrian ways, all 99 taps retained, zero orphan segments. Note that reassignment improves attribution but cannot manufacture information GPS does not contain — at a true shared-node junction (§8) it falls back to continuity.

Robustness across disconnected stretches (v2.9): when a fix has no candidate reachable from any surviving previous state (a GPS jump onto an isolated piece of fetched network, or a hole in OSM coverage), the chain restarts there. The backtrack is piecewise: each connected stretch keeps its own independently optimal solution, instead of one severed boundary discarding the corrections of everything before it. On session 20260520_145913_txb_pkt this recovered 3 fixes that the earlier cascade left uncorrected.

8. Limitations and known cases

Shared-node junctions (irreducible)

Where several ways meet at a shared node, their geometries converge to within sub-metre of each other — an order of magnitude below GPS accuracy. The emission cost is then effectively equal for all of them and topology connects them all, so neither distance nor the adjacency graph can decide which way a tap belongs to. The v2.9 heading term does not resolve this either: at the node itself all converging ways pass through (nearly) the same point, and the GPS bearing through a junction is transitional rather than aligned with any single way. reassignTrajectory keeps continuity (it stays on the way the path was already following), which is the most defensible choice but not a true disambiguation. The 20260520_145913_txb_pkt taps fall into exactly this case; it is an irreducible remainder, not a fixable bug.

Open pedestrian areas

Adjacent pedestrian ways often triangulate an open square, sharing nodes around its edge. “Which line” is not a sharp question inside such a polygon. The matcher gives zero wrong switches on ordinary streets but a handful on a plaza; resolving this properly needs area/pedestrian polygons as snap targets rather than lines.

Vertical coincidence (steps, escalators)

A highway=steps way can sit directly above the walking surface beside it; in 2D they coincide and no horizontal distance distinguishes them. A real fix needs a height signal (barometric altitude, or altitude/altitudeAccuracy from the Geolocation API) or manual marking.

First-fix lock-in

The bootstrap step uses the same stateless nearest-edge logic as the old algorithm. If the first GPS fix of a session falls on the wrong parallel way, the anchor is set there and depth-1/2 filtering will keep it there until the reset threshold trips. Starting a session at a topologically unambiguous location (a junction or a clearly separated street) avoids this. Restarting the session is the user-side fix.

OSM completeness assumption

The algorithm assumes the OSM network around the counter is complete — that every traversable way is mapped, with correct node IDs at intersections. A missing footpath in OSM will cause the depth-1 lookup to fail at that point; depth-2 may also fail if the gap is larger; eventually the reset threshold will fire. The result is a brief gap in attributed taps followed by a clean restart on the other side.

Areas, not ways

The Overpass query filters out elements tagged area=yes. Plazas, courtyards, and similar open spaces are not in the candidate set. A counter standing in the middle of a square has no nearby way to snap to and will produce null snaps (and, after taps, null-or-inherited attributions depending on whether an anchor still exists from before).

Anchor is not persisted

The anchor lives only in memory during the running session. A page reload or crash-recovery restart wipes it; the next fix bootstraps fresh. This is intentional — an old anchor from a previous session is more likely to be wrong than right.

10. Migrating the other apps

The other survey apps in the suite share a common ancestor of the snap module but have diverged. Migration to the adjacency-aware version is a mechanical port:

  1. Change the Overpass query from out tags geom; to out body geom;.
  2. Add SNAP_RESET_M, SNAP_ROAD_FETCH_RADIUS, SNAP_SEGS_RADIUS, snapNodeToWays, snapAdjacency, snapElements, snapAnchorWayId, snapAnchorSegIdx as top-level state.
  3. Add snapRegisterWay(), snapAdjacencySet(), snapDistanceToWay(), snapElementsNear(), snapBuildSegs() helpers.
  4. Replace snapNearestWay() with the decision-ladder version.
  5. In the Overpass response handler, accumulate into snapElements/snapAdjacency first (call snapRegisterWay(el) before storing geometry), then rebuild the candidate segments via snapElementsNear() + snapBuildSegs() — never rebuild the candidate pool from a single fetch (§3).
  6. In the tap handler, fall back to anchor inheritance when a fresh snap returns null.
  7. For sessions that export presence and taps together, add reassignTrajectory() (with splitWayIntoSegments) and call it once at export time, before any CSV is built (§7).

The migration is additive — no existing CSV columns or session formats change. Sessions recorded with the adjacency snap are byte-compatible with the existing telregels.csv and gps.csv schemas; reassignment only changes which (way, segment) the existing columns hold, never the columns themselves.

Out of scope for this document but on the same migration sweep: the platform-robust saveBlob() download helper (iOS-safe export) is a separate, non-snap port that each app needs alongside the above.
